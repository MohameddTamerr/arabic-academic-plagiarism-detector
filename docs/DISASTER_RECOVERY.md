# خطة وسيناريوهات التعافي من الكوارث (Disaster Recovery Plan & Failure Scenarios)
## منظومة كاشف السرقات العلمية الأكاديمي للنصوص العربية — الإصدار v1.4.0-rc

---

## 1. المصفوفة الشاملة للتعافي من الكوارث (DR Scenario Matrix)

| السيناريو والتحدي | السلوك الدفاعي التلقائي للمنظومة | إجراءات التعافي اليدوية / التلقائية | أثر البيانات وسلامة التقارير |
| :--- | :--- | :--- | :--- |
| **1. تلف/فقدان ملف قاعدة البيانات** | إيقاف خوادم التطبيق ورفض العمليات الجديدة | تنفيذ استعادة من آخر نسخة احتياطية معتمدة مع التحقق من البصمات عبر `backup_manifest.json` | العودة لآخر نقطة استعادة سليمة؛ لا تقارير تالفة |
| **2. تلف/فقدان مجلد كائنات التخزين CAS** | كشف فوري عن عدم تطابق البصمات `HASH_MISMATCH` وحظر إصدار التقارير التالفة | استعادة مجلد التخزين المرجعي الأصلي وإعادة التحقق من تكامل الكائنات عبر `storage_service.audit_integrity()` | منع تداول أو اعتماد أي تقرير بمحتوى مفقود |
| **3. تلف أو حذف فهرس الاسترجاع** | فشل منضبط مع كود `ERR_RETRIEVAL_INDEX_UNAVAILABLE` دون تقارير كاذبة | تشغيل أداة إعادة بناء الفهرس الرسمي: `python tools/rebuild_retrieval_index.py` | استعادة الفهرس بنسبة 100% وبشكل فوري |
| **4. انهيار نصف عمال المعالجة (2 من 4)** | انتهاء صلاحية عقود الإيجار (`lease_expires_at`) للمهام المنقطعة | استرجاع المهام تلقائياً عبر العمال المتبقين بنبضات قلب وتوكنات جديدة | لا فقدان للمهام، لا معالجة مزدوجة |
| **5. إعادة تشغيل خادم التطبيق المفاجئ** | استمرار حالة المهام في قاعدة البيانات دون أي اعتماد على ذاكرة التطبيق | إعادة إقلاع سلس؛ إعادة بناء الدفعات `batches` آلياً من حالة قاعدة البيانات | اتساق كامل للحالة والمعاملات |
| **6. انقطاع التخزين المشترك المؤقت** | كشف عجز القراءة/الكتابة وتحويل المهام إلى أخطاء قابلة لإعادة المحاولة المنضبطة | إعادة الاتصال تلقائياً وتكرار المحاولة مع تصاعد التباعد الزمني | لا إنهاء كاذب، لا إيداع جزئي |
| **7. انقطاع قاعدة البيانات المؤقت** | تراجع العمال وتأجيل حجز المهام (`Database Busy / Timeout`) | استئناف الحجز والمعالجة فور عودة قاعدة البيانات للعمل | منع تجزئة الحالة (No Split-Brain) |
| **8. أقفال موزعة عالقة بعد انهيار الحائز** | مراقبة حقل `expires_at` في جدول `distributed_locks` | استيلاء العملية التالية على القفل بعد انتهاء صلاحية الإيجار السابقة | منع الانسداد الدائم (No Deadlock) |

## 2. بروتوكول التعافي من انهيار العمال وإعادة الحجز (Worker Crash Recovery Protocol)

```
[ العامل 1 (PID 18292) ] -----> حجز المهمة T0 (Claim Token: A) -----> [ قيد المعالجة ]
                                                                             |
[ انهيار العامل 1 (SIGKILL) ] ------------------------------------------------+
                                                                             v
[ انقطاع نبضات القلب T2 ] ---> [ انتهاء صلاحية الإيجار T3 ] ---> [ المهمة قابلة للاسترداد ]
                                                                             |
[ العامل 2 (PID 19600) ] <--- استرجاع المهمة T4 (New Token: B) <-------------+
         |
         v
[ إتمام المعالجة T5 ] -------> [ تسليم النتيجة النهائية ] -----> [ تقرير معتمد وحيد ]
```

- **ضمانات البروتوكول:**
  - التوكن القديم (Token A) يُلغى فوراً ولا يمكن استخدامه لإرسال أي نتائج أو تحديثات.
  - النتيجة النهائية تُسجل وتُحفظ لمرة واحدة فقط وبشكل ذري.
  - سجل التدقيق يوثق حدث الاسترجاع وإعادة التعيين بصورة صريحة.

## 3. تعليمات مسؤول الطوارئ (Emergency Administrator Runbook)

1. **فحص صحة النظام العام:**
   ```bash
   python -c "import app.services.system_health_service as shs; print(shs.get_detailed_system_health())"
   ```
2. **استرداد المهام العالقة يدوياً في حال الضرورة:**
   ```bash
   python tools/recover_stale_jobs.py
   ```
3. **التحقق من تكامل التخزين وقاعدة البيانات:**
   ```bash
   python -c "import app.services.storage_service as ss; print(ss.audit_storage_integrity())"
   ```
