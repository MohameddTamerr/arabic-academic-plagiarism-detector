# وثيقة المعايير المؤسسية لنزاهة التقارير واعتمادها وتتبع سلاسل الأدلة
# Academic Report Integrity, Finalization & Evidence Chain Specification

## 1. نظرة عامة (Overview)
توفر هذه الوثيقة الإطار المرجعي والتقني لنظام نزاهة التقارير الأكاديمية وضمان تجميدها وإمكانية استنساخها والتحقق من عدم التلاعب بها داخل المنظومة التي تعمل **محلياً بالكامل (100% Offline)** دون الحاجة لأي خدمات سحابية أو سلاسل كتل (Blockchain) أو بنية تحتية لمفاتيح التوقيع الرقمي العامة الخارجية (External PKI).

---

## 2. دورة حياة كائن التقرير (Report Artifact Lifecycle)

تتكون دورة حياة التقرير التقني من الحالات الصريحة التالية، مع الفصل التام بين **الحالة التقنية للتقرير (Artifact Status)** و **حالة التحكيم الأكاديمي (Review Decision Status)**:

| الحالة التقنية | الوصف والسلوك التشغيلي |
| :--- | :--- |
| `draft` | **مسودة:** تقرير منجز تقنياً حديثاً، قابل لإعادة الحساب والتعديل الإجرائي قبل الاعتماد. |
| `finalized` | **معتمد ومجمد:** تم تجميد كافة مقاييسه وأدلته ومصادره وبصمات ملفاته بحساب بصمة SHA-256 المعيارية. لا يمكن تعديل محتواه إطلاقاً. |
| `superseded` | **مستبدل بإصدار أحدث:** تم إجراء فحص جديد أو مراجعة أحدث لنفس البحث، مع بقاء التقرير التاريخي محفوظاً ومجمداً دون تعديل. |
| `voided` | **مبطل:** تم إلغاء اعتماد التقرير رسمياً لسبب موثق، مع الاحتفاظ بكافة بياناته وبصمته في سجل التدقيق لمنع إخفاء السجلات. |

> [!NOTE]
> لا يتم استبدال أو حذف التقارير التاريخية المعتمدة عند إجراء إعادة فحص (Rescan)، بل يتم تخصيص رقم إصدار جديد (`revision_number = N+1`) وربطه بالإصدار السابق (`supersedes_report_id`).

## 3. التمثيل المعياري الحتمي والبصمة الرقمية (Deterministic Canonical Serialization & SHA-256)

### 3.1 بنية التمثيل المعياري (Canonical Payload)
يتم بناء كائن معياري حتمي يستبعد الحقول المؤقتة والمتغيرة مثل مؤشرات الواجهة وعناوين URL اللحظية، ويشمل:
1. **هوية البحث والتقرير:** المعرف الفريد للتقرير، الرقم المرجعي الرسمي للبحث، رقم الإصدار، ومعرف مهمة الفحص.
2. **المقاييس الأكاديمية:** نسبة الاستلال الإجمالية، النسبة غير الموثقة، النسخ الحرفي، إعادة الصياغة، وعدد الكلمات.
3. **بيان الملفات المدخلة (Input Manifest):** مصفوفة الملفات الأصلية مع أسمائها، ترتيبها، أحجامها، وبصمات SHA-256 المحسوبة لها.
4. **لقطة المراجع (Reference Sources Snapshot):** مصفوفة المراجع المعتمدة التي كُشف التطابق معها مع أرقام الوثائق وعناوينها وإصدار قاعدة المراجع.
5. **شواهد وأدلة الاستلال (Evidence Snapshot):** الشواهد النصية وأرقام الصفحات المصدرية ونسبة المطابقة وحالة التوثيق.
6. **لقطة المعايير والنسخ (Version Snapshot):** إصدارات المحرك، نموذج التطبيع، خوارزميات الاستلال، والعتبات المستخدمة (Jaccard, TF-IDF).

### 3.2 حساب البصمة الرقمية (SHA-256 Checksum)
يتم تحويل الكائن المعياري إلى سلسلة JSON مرتبة المفاتيح حتمياً (`sort_keys=True`) بترميز UTF-8 وحساب بصمة SHA-256 عليها:
$$\text{Finalization Hash} = \text{SHA-256}(\text{Canonical JSON})$$

## 4. ما تثبته بصمة الاعتماد وما لا تثبته (What the Hash Proves vs What it Does NOT Prove)

### ما تثبته البصمة (Tamper-Evidence):
- تثبت البصمة بدقة رياضية مطلقة أن محتويات التقرير ومقاييسه وشواهده وملفاته المدخلة ومعايير فحصه **لم يطرأ عليها أي تعديل أو تلاعب أو تلف** منذ لحظة الاعتماد.
- تمكّن أي مراجع أو مسؤول نظام من إعادة حساب البصمة والتحقق من صحتها في أي وقت بضغطة زر واحدة أوفلاين.

### ما لا تثبته البصمة (Non-Repudiation Disclaimer):
> [!IMPORTANT]
> **إخلاء مسؤولية أمني وهندسي:**
> إن بصمة SHA-256 المعتمدة هي **بصمة كشف تلاعب وتجميد محتوى (Tamper-Evidence Checksum)** وليست توقيعاً رقمياً بمفاتيح غير متناظرة (Digital Signature / Asymmetric PKI). البصمة تثبت عدم تغير البيانات، لكنها لا تثبت هوية الموقع بشكل غير قابل للإنكار (Non-Repudiation) بمعزل عن سجل التدقيق الداخلي (`audit_logs`) وضوابط الجلسات والصلاحيات في المنظومة.

## 5. سياسة التقارير التاريخية (Legacy Reports Policy)
التقارير التي تم إنشاؤها قبل تطبيق المرحلة 15 تُصنف صراحة بحالة:
$$\text{Integrity Status} = \text{legacy\_unverifiable}$$
- تظل التقارير القديمة قابلة للاستعراض والتصدير بالكامل لضمان التوافق التام (Backward Compatibility).
- لا يقوم النظام باختلاق أو تلفيق بصمات تاريخية وهمية لها، بل يعرض إشعاراً مؤسسياً واضحاً بأنها تقارير سابقة لم تخضع للتجميد المعياري وقت إنشائها.

## 6. إجراءات وسلوكيات النظام عند التغييرات (System Behaviors)

### 6.1 إعادة الفحص (Rescan):
1. يتم إنشاء معرف تقرير جديد كلياً (`new_report_id`).
2. يتم زيادة رقم الإصدار تلقائياً (`revision_number = previous + 1`).
3. يتم وسم التقرير السابق بحالة `superseded` مع الحفاظ على بصمته ومحتواه التاريخي دون أي مساس.
4. ترتبط قرارات التحكيم الأكاديمي السابقة بالتقرير القديم وتظل مستقلة عن مراجعة التقرير الجديد.

### 6.2 استبدال أو تحديث ملفات البحث (File Replacement):
- إذا قام المستخدم باستبدال ملفات البحث وإجراء فحص جديد، فإن التقرير المعتمد السابق يحتفظ ببيان ملفاته القديمة وبصماتها الأصلية.
- الفحص الجديد يعتمد بصمات الملفات الجديدة ويبني تقريراً بإصدار مستقل.

### 6.3 التصدير والطباعة (HTML/PDF Export):
- يتضمن التصدير بصمة الاعتماد الرقمية المختصرة، رقم التقرير، رقم الإصدار، والرقم المرجعي للبحث.
- يُحظر كشف المسارات الفيزيائية للأقراص وخوادم التشغيل في وثائق التصدير لحماية الخصوصية.

## 7. مصفوفة الصلاحيات (RBAC Permissions)
| الصلاحية | الكود المعياري | الأدوار المخولة افتراضياً |
| :--- | :--- | :--- |
| **استعراض التقرير والتحقق من النزاهة** | `report.view` | كافة الأدوار (مدخل بيانات، مراجع، مراجع أول، مسؤول وحدة، مدير نظام) |
| **تصدير التقرير** | `report.export` | كافة الأدوار |
| **اعتماد وتجميد التقرير** | `report.finalize` | مراجع أول (`senior_reviewer`)، مسؤول وحدة (`unit_manager`)، مدير نظام (`system_admin`) |
| **إبطال تقرير معتمد** | `report.void` | مسؤول وحدة (`unit_manager`)، مدير نظام (`system_admin`) |
