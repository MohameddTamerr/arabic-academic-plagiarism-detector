# منظومة إدارة طابور المهام والتزامن والأداء (Job Queue & Concurrency Management)

## 1. نظرة عامة (Overview)
تم تصميم منظومة إدارة طابور المهام في المنظومة الأكاديمية لتعمل محلياً بنسبة 100% (Fully Offline) بالاعتماد على محرك SQLite في وضع WAL Transactional Mode دون الحاجة إلى خدمات طوابير خارجية (No Redis, No Celery, No RabbitMQ).

تضمن المنظومة:
- تتبعاً دقيقاً وموثقاً لحالة كل مهمة في الخلفية عبر جدول `job_records`.
- سحباً ذرياً للمهام يضمن رياضياً وهندسياً عدم تكرار المعالجة بين العمليات المتعددة (Multi-Process Atomic Claiming).
- حماية انتقالات الحالات برمز الإيجار (`lease_token`) لمنع العمليات الأخرى أو السابقة من تعديل حالة المهمة الجارية.
- سقفاً صارماً للتزامن يحمي موارد المعالج والذاكرة من الإجهاد.
- جدولة عادلة محددة تمنع الدفعات الكبيرة من احتكار عمال التشغيل وتجويع الأبحاث الفردية (Anti-Starvation).
- إلغاءً تعاونياً آمناً عند نقاط التفتيش يحافظ على سلامة ونزاهة التقارير والفهارس وقاعدة البيانات.
- استعادة ذاتية للمهام المنقطعة عند إعادة تشغيل الخادم وفق مصفوفة تعافٍ واضحة وصريحة.

## 2. مصفوفة وفصل حالات المنظومة (Domain Status Separation & Canonical Mappings)

> [!IMPORTANT]
> **قاعدة الفصل الدلالي للحالات (Semantic State Separation):**
> لا تتماثل حالات سجلات الطابور العامة (`JobRecord.status`) مع الحالات الدلالية لكيانات النطاق (`Research.scan_status` و `ScanBatchItem.status` و `IndexStateRecord.state`). لكل كيان مفرداته وانتقالاته الخاصة والمستقلة.

### أ. الحالات القانونية للبحث (`Research.scan_status`):
وفقاً للمرحلة 5، الحالات المعتمدة حصراً لـ `Research.scan_status` هي:
1. `queued`: البحث في طابور الفحص بانتظار بدء المعالجة.
2. `processing`: جاري تحليل واستخراج ومطابقة البحث.
3. `completed`: اكتمل الفحص التقني بنجاح وتم توليد التقرير.
4. `failed`: تعذر الفحص لوجود خطأ تقني أو تلف في الملف.
5. `interrupted`: انقطع الفحص نتيجة إغلاق أو إعادة تشغيل الخادم.

> [!WARNING]
> يُحظر تماماً كتابة الحالات التالية في `Research.scan_status`:
> - `pending` (مرفوضة حتماً - الحالة القانونية هي `queued`).
> - `cancelled` (مرفوضة حتماً - تُعامل كمهمة منقطعة `interrupted`).
> - `error` (مرفوضة حتماً - الحالة القانونية هي `failed`).
>
> أي محاولة انتقال إلى هذه الحالات تُرفض قطعياً بواسطة `validate_scan_transition`.

#### جدول مواءمة حالات المهمة العامة مع حالة البحث:
| حالة المهمة في الطابور (`JobRecord.status`) | حالة البحث الناتجة (`Research.scan_status`) | التفسير والإجراء |
| :--- | :--- | :--- |
| `queued` | `queued` | البحث في طابور الانتظار |
| `running` | `processing` | جاري الفحص التقني الفعلي |
| `completed` | `completed` | اكتمل الفحص وصدر التقرير بنجاح |
| `failed` | `failed` | فشل الفحص واستنفدت المحاولات |
| `cancel_requested` | الاحتفاظ بالحالة الحالية (`processing`/`queued`) | تبقى الحالة دون تغيير حتى تسوية الإلغاء |
| `cancelled` | `interrupted` | يُثبت الفحص كمنقطع دون تقرير نهائي |
| `interrupted` | `interrupted` | انقطاع الفحص عند الإغلاق المفاجئ |

### ب. حالات عناصر الدفعات (`ScanBatchItem.status`):
يمتلك عنصر الدفعة معجم حالاته الخاص والمستقل في جدول `scan_batch_items`:
- `queued`: العنصر بانتظار دوره في معالجة الدفعة.
- `running`: العنصر قيد المعالجة النشطة حالياً.
- `completed`: اكتمل فحص العنصر بنجاح.
- `error`: فشلت معالجة هذا العنصر تحديداً مع استمرار بقية عناصر الدفعة.
- `interrupted`: انقطعت معالجة العنصر أثناء إعادة التشغيل.

### ج. دورة حياة وحالات الفهرس (`IndexStateRecord.state`):
يحتفظ سجل الفهرس بحالاته الأربع المعتمدة فقط:
- `current`: الفهرس مبني ومطابق تماماً لأحدث إصدار لقاعدة المراجع.
- `stale`: طرأت تعديلات على المراجع وبات الفهرس بحاجة لإعادة بناء.
- `building`: تجري حالياً عملية بناء فهرس جديد في الذاكرة (Staging).
- `failed`: فشلت عملية بناء الفهرس، ويبقى الفهرس السابق الصالح هو النشط.

> [!NOTE]
> عند إلغاء أو انقطاع مهمة إعادة بناء الفهرس (`reference_index_rebuild`)، **لا يتم استحداث حالة جديدة** للفهرس مثل `cancelled` أو `interrupted`؛ بل تظل حالة الفهرس المرجعي إما `stale` أو `failed` وفقاً لدورة الحياة القياسية، ويبقى الفهرس القديم الصالح نشطاً في الذاكرة لمنع انقطاع خدمات الفحص.

## 3. آلية قفل وقواعد ذرية السحب في SQLite (SQLite Claiming Atomicity)
> [!IMPORTANT]
> **توضيح مصطلحات القفل:** قاعدة بيانات SQLite لا توفر أقفالاً على مستوى الصفوف (No row-level write locks) كقواعد البيانات الشبكية، وإنما تعتمد على قفل كتابة واحد على مستوى ملف قاعدة البيانات في وضع WAL.

تتحقق الذرية التامة ومنع التكرار (At-most-once claim guarantee) عبر خوارزمية السحب التالية:
1. بدء المعاملة وفحص سعة التزامن للأنواع النشطة (`running`).
2. استعلام المهام المؤهلة ذات الحالة `status = 'queued'` و`retry_at <= now` مرتبة حسب الأولوية (`priority DESC`) ثم وقت الإدراج (`queued_at ASC`).
3. تطبيق التحديث الشرطي الذري (Conditional Atomic UPDATE) على المهمة المختارة:
   ```sql
   UPDATE job_records
   SET status = 'running',
       started_at = :now,
       heartbeat_at = :now,
       worker_pid = :pid,
       lease_token = :lease_token,
       attempt_count = attempt_count + 1,
       stage = 'بدء التنفيذ'
   WHERE id = :job_id AND status = 'queued';
   ```
4. فحص عدد الصفوف المتأثرة (`rowcount`):
   - إذا كان `rowcount == 1`: نجح السحب للعملية الحالية حصرياً وثُبت رمز الإيجار `lease_token`.
   - إذا كان `rowcount == 0`: يعني ذلك أن عملية متزامنة أخرى سحبت نفس المهمة في نفس اللحظة، فيتم الانتقال ذرياً للمرشح التالي دون أي تعارض.
5. اعتماد المعاملة (`COMMIT`).

## 4. منع تكرار بناء الفهرس ذرياً (DB-Atomic Index Rebuild Deduplication)
- لمنع إنشاء مهام بناء فهرس مكررة لنفس الإصدار المرجعي (`target_corpus_version`) تحت ضغط الطلبات المتزامنة عبر عمليات نظام التشغيل، تستخدم دالة `enqueue_job` معاملة فورية (`BEGIN IMMEDIATE;`).
- تحجز `BEGIN IMMEDIATE;` قفل الكتابة على مستوى SQLite فوراً، ثم تفحص وجود أي مهمة نشطة في حالة `queued` أو `running` لنفس الإصدار.
- إذا وجدت مهمة نشطة مسبقاً، يُعاد معرف المهمة القائمة مباشرة للمستدعي دون إدراج أي سجل مكرر، وتلتزم كافة العمليات المتزامنة بنفس المهمة الوحيدة المجدولة.

## 5. حماية التزامن للنسخ الاحتياطي وOCR عبر العمليات المتعددة (Process Synchronization)

### أ. قفل النسخ الاحتياطي عبر العمليات (`CrossProcessBackupLock`):
- لا تكتفي المنظومة بضبط `MAX_CONCURRENT_BACKUPS = 1` على مستوى الطابور أو الأقفال المحلية للعملية (`threading.Lock`)؛ بل تُعيد استخدام آلية القفل الذري على مستوى نظام التشغيل (`CrossProcessBackupLock`).
- يعتمد القفل على إنشاء ملف القفل `.backup.lock` ذرياً عبر نداء النظام `os.open(..., os.O_CREAT | os.O_EXCL | os.O_RDWR)`.
- يضمن ذلك استحالة دخول أكثر من عملية نظام تشغيل واحدة إلى المنطقة الحرجة لإنشاء النسخ الاحتياطي في نفس اللحظة، مع توفير آليات استرداد للأقفال الميتة (`Stale Locks`) وفحص حياة رقم العملية (`PID`).

### ب. حماية فتحة تنفيذ OCR عبر العمليات (`MAX_CONCURRENT_OCR_JOBS = 1`):
- **الحد المعتمد لنطاق النشر المؤسسي:** `MAX_CONCURRENT_OCR_JOBS = 1` تعني حتمياً: تشغيل **استدعاء Tesseract فعلي واحد فقط** في نفس اللحظة عبر كافة عمليات الخادم / العمال (`Application / Worker OS Processes`) المتشاركة لنفس وحدة التخزين وقاعدة البيانات.
- **التمييز بين الحماية المحلية والحماية الشاملة:**
  - `threading.Semaphore(MAX_CONCURRENT_OCR_JOBS)`: يمثل حارساً محلياً داخل العملية الواحدة فقط (`Intra-process optimization`) لتنظيم مسارات الخيوط.
  - `CrossProcessOcrLock`: يمثل الحد الفاصل والموثوق تشغيلياً على مستوى نظام التشغيل عبر كافة العمليات المستقلة (`Authoritative Cross-Process Boundary`).
- **آلية القفل الذرية على مستوى نظام التشغيل:**
  - يتم إنشاء ملف القفل `.ocr.lock` ذرياً عبر نداء النظام الحصري `os.open(..., os.O_CREAT | os.O_EXCL | os.O_RDWR, 0o600)`.
  - تُخزن بيانات وصفية داخل القفل تشمل (`token`, `owner`, `pid`, `acquired_at`, `expires_at`).
  - يلتف القفل مباشرة حول الاستدعاء الفعلي الثقيل لمحرك الاستخراج: `pytesseract.image_to_string` داخل كتلة `try ... finally` تضمن التحرير الحتمي عند النجاح أو الفشل أو الإلغاء.
- **معاملات التكوين والتحكم:**
  - `MAX_CONCURRENT_OCR_JOBS`: قيمة تشغيلية ثابتة = `1` (تصميم قفل الملف الحصري الحالي يدعم فتحة تنفيذ عالمية واحدة Single Exclusive Slot، ولا يدعم أعداد N>1 اعتباطية).
  - `OCR_LOCK_TIMEOUT_SECONDS`: مهلة حجز القفل القصوى (افتراضياً `60` ثانية قابلة للتعديل عبر البيئة).
  - **سلوك الانتظار:** انتظار محدد (`Bounded Wait`) مع محاولات متكررة كل `100ms` حتى انقضاء المهلة المحددة، ثم إرجاع خطأ آمن عند تعذر الحصول على الفتحة.
  - **التعافي من الأقفال الميتة (`Stale Lock Recovery`):** عند وجود قفل سابق، يتم فحصه ذرياً: إذا انتهت مدة الصلاحية (`time.time() > expires_at`) أو كانت العملية المالكة قد توفيت (`PID no longer exists` عبر `OpenProcess`/`kill(0)`)، يتم تنظيف القفل واسترداده تلقائياً دون الحاجة لأي تدخل يدوي، مع حظر حذف أي قفل تابع لعملية نشطة حية.

## 6. حماية ملكية الإيجار (Lease Ownership Contract)
عند سحب المهمة، يُنشأ رمز إيجار فريد (`lease_token = uuid.uuid4().hex`) ويُخزن في سجل المهمة.
يُشترط رمز الإيجار لحماية كافة انتقالات الحالة والعمليات التشغيلية:
- **نبض الحياة (`heartbeat_job`):** يرفض التحديث إذا كان رمز الإيجار غير متطابق.
- **اكتمال المهمة (`complete_job`):** يرفض حفظ النتائج والانتقال إلى `completed` من أي عملية لا تملك نفس الإيجار.
- **تسجيل الفشل (`fail_job`):** يرفض الانتقال إلى `failed` أو إعادة الجدولة برمز إيجار خاطئ.
- **تأكيد الإلغاء (`finalize_cancellation`):** يرفض التثبيت والتنظيف دون رمز الإيجار الصالح.

## 7. نبض الحياة ورصد المهام العالقة (Heartbeat & Stuck Detection)
### سلوك نبض الحياة أثناء التشغيل:
- **الفاصل الزمني لنبض الحياة:** يتم ضبطه عبر `JOB_HEARTBEAT_INTERVAL_SECONDS` (افتراضياً `10` ثوانٍ).
- **الأنواع التي تدعم نبض الحياة:** `scan`, `batch_scan`, `thesis_scan`, `reference_index_rebuild`, `integrity_check`, `backup`.
- **كبح الكتابة (Throttling):** لا تُكتب نبضات متكررة في قاعدة البيانات إذا كان الفارق الزمني أقل من `5` ثوانٍ، ما لم تتغير المرحلة (`stage`) أو نسبة التقدم (`progress`).
- **التوقف عند الحالة النهائية:** يتوقف نبض الحياة فور تحول المهمة إلى حالة نهائية (`completed`, `failed`, `cancelled`, `interrupted`).

### رصد المهام العالقة (Stuck Job Detection):
تُعتبر المهمة "عالقة" (`stuck`) إذا تحققت كافة الشروط التالية:
1. `status == 'running'`
2. عمر آخر نبض حياة `heartbeat_at` (أو `started_at` في حال عدم وجود نبضات) يتجاوز `JOB_STUCK_HEARTBEAT_MINUTES` (افتراضياً `5` دقائق).
3. نوع المهمة يدعم نبض الحياة.

> [!NOTE]
> نظام المراقبة وصحة النظام في Phase 11 **لا يقوم بقتل أو إنهاء المهام العالقة تلقائياً**، بل يُبلغ عنها بحالة `degraded` في لوحة التشغيل لاتخاذ القرار الإداري الواعي.

## 8. مصفوفة الاستعادة والتعافي عند إعادة التشغيل (Restart Recovery Matrix)

عند إقلاع خادم التطبيق، يتم تشغيل `job_queue_service.recover_interrupted_jobs()` حتمياً لفحص كافة المهام التي كانت في حالة `running` أو `cancel_requested` وتحويلها وفق المصفوفة التالية:

| نوع المهمة (`job_type`) | حالة ما بعد الإقلاع | هل المهمة منقطعة؟ (`interrupted`) | إعادة المحاولة التلقائية | هل تتطلب تدخلاً يدوياً؟ | ملاحظات السلامة |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `scan` | `interrupted` | نعم | نعم (عبر سياسة المحاولات أو يدوياً) | لا | لا تترك أي تقرير جزئي |
| `batch_scan` | `interrupted` | نعم | نعم (للعنصر المتأثر فقط) | لا | لا تؤثر على بقية عناصر الدفعة |
| `thesis_scan` | `interrupted` | نعم | نعم | لا | يعاد فحص الفصول غير المكتملة |
| `reference_index_rebuild` | `interrupted` | نعم | نعم (يمكن طلب إعادة البناء) | لا | يظل الفهرس القديم الصالح نشطاً |
| `integrity_check` | `interrupted` | نعم | لا | نعم | يتطلب تشغيل فحص نزاهة جديد |
| `backup` | `interrupted` | نعم | لا | نعم | تُحذف الملفات المؤقتة ويتطلب إنشاء نسخة جديدة |
| `restore` | `interrupted` | نعم | **ممنوع قطعاً (NO)** | **نعم (حتمي)** | **عمليات الاستعادة المدمرة لا يُعاد تشغيلها تلقائياً أبداً** |
| `report_export` | `interrupted` | نعم | نعم | لا | يعاد التصدير عند الطلب |

### الفرق بين `interrupted` و`failed`:
- **`failed`:** وصل عامل التشغيل إلى نهاية مسار المعالجة مع تسجيل خطأ واضح (مثل ملف تالف أو استنفاد المحاولات).
- **`interrupted`:** توقف التنفيذ بصورة مفاجئة وغير متوقعة (انقطاع التيار، إغلاق الخادم، أو اختفاء العملية).

## 9. الجدولة العادلة ومنع التجويع (Fairness & Anti-Starvation Policy)
تعتمد المنظومة خوارزمية جدولة حتمية محكمة:
1. عند اختيار المهمة التالية من أعلى 10 مهام مؤهلة، تُفحص الدفعات الجارية حالياً (`active_batch_ids`).
2. إذا كان أول مرشح ينتمي لدفعة يجري تشغيل عنصر منها حالياً، يبحث المجدول عن بحث مستقل (`standalone scan`) أو عنصر من دفعة أخرى شاغرة ضمن المرشحين لتقديمه.
3. يضمن ذلك توزيع عمال التشغيل بين الدفعات والأبحاث المستقلة بالتناوب، مانعاً أي دفعة ضخمة (مثال: 50 بحثاً) من احتكار كافة مسارات الفحص.

## 10. سياسة التراجع الزمني وإعادة المحاولة (Bounded Retries & Backoff)
- **عداد المحاولات (`attempt_count`):** يزداد فقط عند سحب المهمة للتنفيذ الفعلي (`claim`)، ولا يزداد عند الإدراج أو إعادة الجدولة.
- **التراجع الزمني دون تجميد الخيوط (No Thread Sleeps):**
  يُحسب وقت المحاولة القادمة ويوثق في `retry_at`:
  - المحاولة 1: تأخير `5` ثوانٍ (`retry_at = now + 5s`).
  - المحاولة 2: تأخير `30` ثانية (`retry_at = now + 30s`).
  - المحاولة 3: تأخير `120` ثانية (`retry_at = now + 120s`).
  يتجاوز استعلام السحب المهام التي تمتلك `retry_at > now` تلقائياً دون أي حجز أو تعليق لمسارات العمل.

## 11. مصفوفة قابلية ونقاط تفتيش الإلغاء (Cancellation Policy Matrix)

| نوع المهمة (`job_type`) | إلغاء وهي في الطابور (`queued`) | إلغاء وهي قيد التشغيل (`running`) | نقاط التفتيش الآمنة | إجراءات التعافي |
| :--- | :--- | :--- | :--- | :--- |
| `scan` | نعم (فوري) | نعم (تعاوني) | بين الاستخراج، واسترجاع المرشحين، ومطابقة المتواليات | تنظيف الملفات المؤقتة، عدم حفظ تقرير |
| `batch_scan` | نعم (فوري) | نعم (تعاوني) | بين مراحل معالجة الملف | إلغاء العنصر مع استمرار الدفعة |
| `thesis_scan` | نعم (فوري) | نعم (تعاوني) | بين استخراج الفصول | تنظيف مجلد الرسالة المؤقت |
| `reference_index_rebuild` | نعم (فوري) | نعم (تعاوني) | قبل اعتماد الترقية النهائية | التخلص من الفهرس المرحلي، بقاء الفهرس القديم |
| `integrity_check` | نعم (فوري) | نعم (تعاوني) | بين دفعات الكيانات | إيقاف الفحص دون تعديل البيانات |
| `backup` | نعم (فوري) | نعم (تعاوني) | قبل مرحلة الضغط وحساب البصمة | حذف الأرشيف المؤقت غير المكتمل |
| `restore` | **لا (حذر)** | **ممنوع أثناء الكتابة** | لا توجد نقاط آمنة أثناء استبدال الملفات | مراجعة سلامة قاعدة البيانات يدوياً |
| `report_export` | نعم (فوري) | نعم (تعاوني) | قبل كتابة الملف النهائي | حذف الملف المصدر جزئياً |

## 12. ترقية الفهرس على نظام ويندوز (Windows Index Promotion)
- نظراً لطبيعة نظام تشغيل Windows التي تفرض قيوداً على استبدال أو حذف الملفات المفتوحة (`file lock semantics`)، تُبنى فهارس الاسترجاع الجديدة في الذاكرة في كائن مرحلي منفصل.
- تتم الترقية ذرياً عبر تبديل المؤشر المرجعي في الذاكرة (`_CACHED_INDEX`) وتحديث سجل `IndexStateRecord` إلى `current` داخل معاملة واحدة.
- في حال حدوث أي استثناء أثناء البناء، يتم التراجع ولا يتأثر الفهرس النشط القديم ويبقى متاحاً لجميع عمليات الفحص دون انقطاع.

## 14. سياسة الاحتفاظ والخصوصية (Retention & Privacy Policy)
- **تنظيف السجلات القديمة:** تحذف دالة `cleanup_completed_jobs(retention_days=30)` سجلات المهام المنتهية فقط (`completed`, `cancelled`, `failed`) التي تجاوزت مهلة الاحتفاظ.
- **سلامة التقارير وسجلات التدقيق:** لا تُحذف التقارير الأكاديمية (`reports`) ولا سجلات التدقيق (`audit_logs`) ولا بيانات الأبحاث بتنظيف الطابور؛ حيث تظل محفوظة في جداولها المخصصة لضمان النزاهة التاريخية.
- **عزل خصوصية واجهات البرمجة:** تمنع واجهات `/api/jobs` المستخدمين العاديين من استعراض أو تخمين مهام زملائهم، وتعيد `403 Forbidden` عند محاولة الوصول غير المصرح.
